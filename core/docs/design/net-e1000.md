# The oscortex network driver — Intel 82540EM (`8086:100E`), a design

**Status: DESIGN. Not an ADR, not numbered, nothing implemented, no code written and no kernel
built.** This document exists so that the agent who builds the first piece does not have to
re-decide anything, and so that the two premises this unit was handed — both of which turned out to
be wrong — are corrected once, here, rather than discovered separately by each reader.

**The two corrections, up front, because everything downstream moves if you believe the old
versions.**

1. **"Given no allocator" is no longer true.** M7 landed `core/kernel/pmm.dart`. `allocFrame()`
   returns a 4KiB physical address and `freeFrame(addr)` takes it back, with a double-free check.
   The M6-era shape — *"this driver can SHOW you a sector and cannot GIVE you one"* (ADR-0010 §5) —
   was forced by an absence that has since been filled. §3 spends the allocator rather than routing
   around it, and says exactly how many frames.
2. **There is no PIO escape hatch for this device.** ATA had one, and ADR-0010 §3 is the argument
   that taking it was structural rather than lazy. The e1000 has an I/O-space BAR that looks like
   the same door, and under QEMU **it is a stub that returns zero and discards writes** (§1.3, and
   I read the source). The register set is reachable through memory-mapped I/O or not at all, and
   packets move by bus-master DMA or not at all. **This driver cannot be built in the shape M6 was
   built in.**

### The six things decided here, for a reader in a hurry

| | decision | where |
|---|---|---|
| **Registers** | **BAR0, MMIO, 32-bit accesses only.** The I/O BAR is a decoy. And the mapping *already exists* — `vmBuild` maps all of `[3GiB, 4GiB)` and BAR0 lands at `0xFEBC0000`. | §1.2, §1.3 |
| **Config space** | **The kernel must learn to WRITE it**, for one bit: bus-master enable. That is the first `outl` to `0xCFC` this kernel has ever done, and without it every DMA silently does nothing. | §1.4 |
| **MAC** | **Read `RAL0`/`RAH0`**, and read the EEPROM through `EERD` as well — not for redundancy, but because RAL/RAH is what checks that our EERD bit-layout decoding is right. | §2.3 |
| **Ring memory** | **`allocFrame()`, seven frames, 28 KiB.** The identity map is what makes this expressible at all: below 128 MiB, virtual address == physical address, so a pointer the kernel can dereference is a descriptor address the NIC can use. | §3 |
| **Interrupts** | **Poll first.** IRQ 11 is on the *slave* PIC, which this kernel has never unmasked, never EOI'd, and whose cascade line is masked. That is a real milestone in `interrupts.dart`, not a flag. | §5 |
| **Verification** | **`-object filter-dump` for the packet bytes, slirp's *reply* for the semantics.** A reply from an independent TCP/IP implementation is the strongest evidence available here, and it is unfakeable by a kernel that is printing rather than transmitting. | §7 |

**What to build first: N0 (§8) — name the device and read its BAR.** It is one PCI walk and one
print, it is the first thing every later milestone depends on, and its exit criterion compares the
number the kernel printed against QEMU's own `info pci` — two independent observers of one fact.

**And the finding that would have cost somebody a day.** With a default `-device e1000`, **the
option ROM drives the card during POST**: a boot that never reaches the kernel already puts seven
packets in the pcap, including a full DHCP exchange. Any exit criterion of the form *"the capture is
non-empty"* is vacuous. §7.2 is the fix, and it is one flag.

## 0. What this has to be true of

Five constraints, all properties of this machine rather than tastes.

1. **`@bare` DCDart is a small language**, and the sub-language a device driver needs is not the one
   a compositor needs. §6 lists what helps, what hurts, and the one place the language is
   *better* than C for this job.
2. **Every milestone needs a mechanically-checked, pass/fail exit criterion** (CLAUDE.md rule 2).
   "The link came up" is not one. "The bytes in the host's capture equal the bytes the harness
   derived" is.
3. **Nothing ever waits.** GAP-0141: no blocked state, no sleep, no wakeup. Every wait in this
   driver is a bounded spin in task context, exactly as `ataWait` is, with the same
   iteration-count-not-duration caveat (GAP-0073).
4. **The kernel is one compilation unit.** `core/kernel/net.dart` will be a `part of 'kmain.dart'`
   for GAP-0004 item 4's reason, like every other kernel file.
5. **A NIC is the first device on this machine that writes to memory on its own.** Everything to
   date moved bytes through the CPU — `in`/`out`, or a store to a framebuffer. The e1000 reads and
   writes RAM at physical addresses it was handed, asynchronously, with no reference to CR3, the
   page tables, W^X or the process that is running. §3.4 is what that means and what it costs.

## 1. Finding the device, and making it usable

### 1.1 The bus walk retains nothing, so this driver walks it again

GAP-0067 item 1: `pci.dart` prints as it walks and keeps no device list. `fb.dart` already pays this
bill — `fbFindBar0` re-walks bus 0 looking for class `03`, reads BAR0, and returns it. This driver
does the same for class `02`, subclass `00`:

```
netFindDevice() -> a packed bus/dev/fn, or a sentinel meaning "none"
```

**One value out, because `@bare` DCDart returns one value and has no out-parameters** (the constraint
`fat.dart` documents at `fatAlloc`). Pack `bus`, `dev`, `fn` into one `u64` — `(bus << 16) | (dev <<
11) | (fn << 8)` is already the selector shape `pciAddr` wants, so the packing is not an encoding,
it is the thing the next call needs anyway. Sentinel: `0xFFFFFFFF`, which no legal selector can be.

**Bus 0 only, deliberately**, matching `fbFindBar0`. `m5-pci` has a boot that puts the e1000 behind
a `pci-bridge` at `01:02.0` (`m5-pci/run.sh:1096`) — under that topology this driver would print
`NET NONE` and be *right to*, and the recursive search is a named successor rather than a defect.

### 1.2 BAR0, and the pleasant surprise

BAR0 is at configuration offset `0x10`. Bit 0 distinguishes memory from I/O; bits 2:1 encode the
width; bit 3 is prefetchable. The address is `bar & 0xFFFFFFF0`. This is `fbFindBar0`'s arithmetic
exactly, and `fb.dart:314` already writes the reasoning down.

**The surprise is that no mapping work is needed.** I expected this to be the blocker — a device
register window above the top of managed RAM, needing a new page-directory entry and a `PCD` bit,
the way §1.2 of the display design found the 2 MiB user window to be the real constraint. It is not:

> `vm.dart:1134` — *"`PD_pci[0..511]` -> 2MiB pages, `[3GiB, 4GiB)`, writable and NX."*

`0xFEBC0000` is in that range. **M5 already paid for this**, for the framebuffer, and `vmCheckPage`
even asserts the PCI hole's first page is present. A `Pointer<u32>.fromAddress(bar0 + off)` works on
the first try.

**Two things about that mapping which are true and untested.** It is **2 MiB pages**, so the 128 KiB
BAR shares a page with whatever else the firmware put in `0xFEA00000–0xFEBFFFFF` — nothing, on this
machine, but the granularity is not ours. And it is **write-back, with no `PCD`/`PWT`**: on QEMU
irrelevant (every access is a memory-region dispatch), on hardware saved only by the MTRRs, which
mark the PCI hole uncacheable and which this kernel never programs or reads. **A device register
window mapped WB with no MTRR is a real bug on real hardware**, it is invisible here, and it belongs
in `known-gaps.md` whether or not this driver is ever built.

### 1.3 The I/O BAR is a decoy, and this is the load-bearing negative result

BAR1 is 64 bytes of I/O space at `0xC000`. On a real 82540EM those 64 bytes are `IOADDR` (offset 0)
and `IODATA` (offset 4): write the MMIO offset to one, read or write the register through the other.
That is an indirect path to the whole register set **using nothing but `Port.inl`/`Port.outl`** — no
mapping, no pointers, no MMIO at all. It is the exact shape of ADR-0010's argument for PIO, and if
it worked it would be the right answer for the same reason.

It does not work. QEMU's `hw/net/e1000.c`:

```c
static uint64_t e1000_io_read(void *opaque, hwaddr addr, unsigned size)
{
    E1000State *s = opaque;
    (void)s;
    return 0;
}

static void e1000_io_write(void *opaque, hwaddr addr, uint64_t val, unsigned size)
{
    E1000State *s = opaque;
    (void)s;
}
```

**Reads return zero. Writes are discarded.** A driver written against BAR1 would read `STATUS` as
`0`, conclude the link is down, and never transmit — and every one of its register writes would land
nowhere, with no fault, no diagnostic, and a perfectly healthy-looking machine.

Worth stating as a rule rather than a fact about one device: **an emulated device's "compatibility"
register path is not necessarily emulated.** The presence of a BAR says the address space is
decoded, not that anything is behind it.

### 1.4 The kernel must learn to write configuration space, for one bit

GAP-0067 item 2 predicted this milestone by name:

> *"No `port_outl` to `0xCFC` anywhere. That rules out, today: enabling memory or I/O decoding in the
> command register, **setting the bus-master bit (needed by every DMA-capable device)** …"*

The command register is configuration offset `0x04`, low 16 bits. Bit 1 is memory-space enable; **bit
2 is bus-master enable**, and without it the NIC is not permitted to originate a transaction on the
bus at all. Every descriptor fetch, every packet DMA, every status writeback is a bus-master
transaction. **With BME clear, a completely correct driver transmits nothing and reports no error**
— TDT advances, TDH does not, DD is never written, and the bounded wait expires.

SeaBIOS enables memory and I/O decoding for every device it finds; it sets BME only for devices it
boots from. **Do not assume; read it, set it, and print both values.**

`pciWrite32` is four lines and reuses the existing `port_outl`. **One subtlety that is silently
destructive if missed:** configuration mechanism #1 is doubleword-only, so writing the command
register means writing offset `0x04` as a dword — and the *upper* half of that dword is the **status
register**, whose error bits are write-1-to-clear. Reading the dword and writing it straight back
would clear whatever errors the device had latched. The correct idiom is:

```
val = pciRead32(...,0x04) & 0xFFFF     // keep the command half, zero the status half
pciWrite32(...,0x04, val | 0x06)       // MEM | BME; writing 0 to a W1C bit is a no-op
```

**This also puts a second writer on the `0xCF8`/`0xCFC` pair**, which GAP-0067 item 6 already calls
non-atomic. It does not make that hazard worse today (a config write happens once, at task level,
with only IRQ1 unmasked, and `kbdHandle` touches neither port) and it does make it *closer*, because
an IRQ-driven version of this driver would be a handler with a legitimate reason to touch
configuration space.

## 2. The register set actually needed

About thirty registers of the 128 KiB window, and no more. Every offset and bit below was checked
name by name against QEMU's `e1000x_regs.h` and
`e1000_regs.h` by name. **All accesses are 32-bit** — the e1000's register file is dwords, and a
byte or word access to it is not a narrower version of the right thing, it is undefined.

### 2.1 Control, status, interrupts

| name | off | what this driver does with it |
|---|---|---|
| `CTRL` | `0x0000` | `RST` = `0x04000000` to reset; then `SLU` = `0x40` (set link up), `ASDE` = `0x20` (auto-speed detect). `LRST` = `0x08` must be **clear**. |
| `STATUS` | `0x0008` | read-only. `LU` = `0x02` is link-up; `FD` = `0x01` is full duplex. The link check, and the only proof the reset finished. |
| `EERD` | `0x0014` | EEPROM read — §2.3. |
| `ICR` | `0x00C0` | interrupt cause, **read-to-clear**. Must be read to deassert a level-triggered INTx. |
| `ICS` | `0x00C8` | write-to-set-cause. **The only way to test the IRQ path without a packet** — see N7. |
| `IMS` | `0x00D0` | interrupt mask set. `RXT0` = `0x80`, `TXDW` = `0x01`, `LSC` = `0x04`. |
| `IMC` | `0x00D8` | interrupt mask clear. `IMC = 0xFFFFFFFF` **twice** — once before `CTRL.RST` and once after, because the reset re-enables some causes. |
| `FCAL`/`FCAH`/`FCT`/`FCTTV` | `0x28`/`0x2C`/`0x30`/`0x170` | all written **zero**: 802.3x flow control off. Four stores that look like superstition and are not — a card that negotiates PAUSE frames and has nowhere to send them is a card that stops. |
| `MTA` | `0x5200` | 128 dwords of multicast hash. Written to zero. QEMU resets them to zero already; hardware does not guarantee it. |
| `RA` | `0x5400` | `RAL0` at `0x5400`, `RAH0` at `0x5404`. `AV` = `0x80000000` in `RAH` is the valid bit. |

### 2.2 The rings

| name | RX | TX |
|---|---|---|
| base low / high | `RDBAL 0x2800` / `RDBAH 0x2804` | `TDBAL 0x3800` / `TDBAH 0x3804` |
| length in **bytes** | `RDLEN 0x2808` | `TDLEN 0x3808` |
| head (device) | `RDH 0x2810` | `TDH 0x3810` |
| tail (software) | `RDT 0x2818` | `TDT 0x3818` |
| control | `RCTL 0x0100` | `TCTL 0x0400` |
| — | `RDTR 0x2820` = 0 (no receive delay) | `TIPG 0x0410` = `0x0060200A` |

`RCTL` bits: `EN` `0x02`, `UPE` `0x08` (unicast promiscuous), `MPE` `0x10`, `LPE` `0x20` (long
packets), `BAM` `0x8000` (**accept broadcast — an ARP reply to `ff:ff:ff:ff:ff:ff` is dropped
without it**), `SZ_2048` = `0x00000000` (the default buffer size, which is why §3.3 chooses 2048),
`BSEX` `0x02000000`, `SECRC` `0x04000000` (strip the Ethernet CRC — **set it, or every received
length is four bytes longer than the frame and the harness comparison fails by four bytes**).

`TCTL` bits: `EN` `0x02`, `PSP` `0x08` (pad short packets), `CT` mask `0x0FF0` (collision threshold,
`0x10`), `COLD` mask `0x003FF000` (collision distance, `0x40` for full duplex → `0x40 << 12`).

**Counters worth reading, because M14 established that a number is worth more than an adjective**
(`fatMetaReads`/`fatMetaHits`): `TPT` `0x40D4` total packets transmitted, `TPR` `0x40D0` total
received, `GPTC` `0x4080`, `GPRC` `0x4074`, `CRCERRS` `0x4000`. These are the device's own count,
maintained inside the NIC, independent of anything the driver believes — which makes
`TPT == 1` a fact about the *hardware* in a way that `netTxCount == 1` is not.

### 2.3 The MAC address: read both, and know which one is the truth

Two sources, and they are not redundant.

**`RAL0`/`RAH0`** is the receive-address filter. It is what the device actually matches incoming
frames against, so it is *the* MAC in every sense that affects behaviour. QEMU's `e1000_reset` calls
`e1000x_reset_mac_addr()`, which copies the `mac=` property into `RA`, so it is valid immediately
after reset with no EEPROM access at all. Six bytes: `RAL` holds bytes 0–3 little-endian, `RAH` bits
15:0 hold bytes 4–5.

**`EERD`** is the EEPROM. The 82540EM layout — confirmed against `e1000x_regs.h`:

```
  write:  (word_addr << 8) | 1              START = 0x01, ADDR_SHIFT = 8
  poll:   until (read & 0x10) != 0          DONE  = 0x10
  data:   (read >> 16) & 0xFFFF             DATA_SHIFT = 16
```

Words 0, 1, 2 hold the MAC, **two bytes per word, low byte first**. Note that this layout is *not*
the one 82541-and-later parts use (address at bits 15:2, done at bit 1) — a driver that reads a
device ID and picks a layout would be more general and would also be untestable here, since QEMU
gives us exactly one part.

**Recommendation: read both, print both, and have the harness require them equal.** On QEMU they
come from the same property, so this is **not** an independent cross-check of the MAC — it is a
check that our EERD *bit-layout decoding* is right, which is the part most likely to be wrong and
the part that silently produces a plausible-looking wrong MAC. Say that in the ADR; do not let the
assertion look stronger than it is.

## 3. Where the ring memory comes from

### 3.1 The premise that expired

The task this document answers said *"given no allocator"*. That was true at M6 and stopped being
true at M7. `pmm.dart` manages 128 MiB in 4 KiB frames; `allocFrame()` returns a physical address or
**0 on failure** (0 being unambiguous because the first megabyte is reserved), and `freeFrame(addr)`
returns a status code and refuses double frees.

So the honest framing is not *"where do we put a ring with no allocator"* but **"this is the first
milestone that spends the allocator on hardware, and here is the bill."**

### 3.2 The property that makes DMA expressible at all

**Below 128 MiB, virtual address == physical address.** `boot.S` identity-maps it, `vmBuild`
re-establishes it with 2 MiB leaves, and `vm.dart:62` states it: *"Identity throughout — virtual
address == physical address."*

That single fact is why this driver is buildable in DCDart. A descriptor's buffer field is a
**physical** address; a `Pointer<u64>` holds a **virtual** one; and here they are the same number,
so no translation function has to exist, no `virt_to_phys` has to be written, and no bug of the form
"the NIC read the wrong page" is possible from that direction.

**It is also a dependency nothing declares.** The moment anything maps kernel data anywhere but the
identity window, this driver breaks silently — the NIC keeps DMAing to the old physical address.
Whoever writes N0 should put that sentence in `net.dart`'s header.

### 3.3 The recommendation: seven frames, 28 KiB

| what | frames | why that size |
|---|---|---|
| TX descriptor ring | 1 | 8 descriptors × 16 B = **128 bytes**. `TDLEN` must be a multiple of 128 and the base 16-byte aligned; 128 is the smallest legal ring and a whole frame guarantees both alignments without arithmetic. The rest of the frame is wasted, and deliberately: sharing it invites an offset bug that presents as a NIC writing into somebody else's data. |
| RX descriptor ring | 1 | same, 8 descriptors. |
| RX packet buffers | 4 | 8 × 2048 B = 16 KiB, two buffers per frame at offset 0 and 2048. 2048 is `RCTL.SZ_2048` = `0`, i.e. the reset default — the fewest register bits that have to be right. |
| TX packet buffer | 1 | one frame, one frame at a time. A 1514-byte Ethernet frame fits with room over. |

**Alternatives, and why not:**

* **`@bss` with `align:`** genuinely works — `Bss(bytes: 4096, align: 4096)` is expressible
  (`proc.dart:981` already passes `align: 16`), the kernel image is inside the identity window, so a
  `@bss` address is a physical address, and it costs zero allocator frames. It costs 28 KiB of
  *permanent* image-resident state for a device that may not be present, and M17's whole subject was
  getting 13,952 donated bytes back. **Use `@bss` only for the small stuff** (§3.5).
* **4096-byte buffers via `RCTL.BSEX`** would make it one frame per packet and delete the
  offset-2048 arithmetic. It costs two more register bits that have to be exactly right, and buys
  nothing until jumbo frames exist. Named successor, not now.
* **A bigger ring.** 8 descriptors is the legal minimum and is more than a one-packet-at-a-time
  driver can use. Growing it is one constant.

### 3.4 What DMA does not respect, listed rather than discovered

**This is the section to read twice.** A NIC with bus-master enabled is a second thing that writes
to memory, and *none* of the machinery M8–M12 built applies to it:

* **Not paging.** The device uses physical addresses. CR3 is irrelevant, the page tables are
  irrelevant, and there is no fault path — a descriptor pointing at the wrong frame is a silent
  write into RAM nothing tracks, which is precisely the failure mode `vm.dart` congratulates itself
  on having abolished for the CPU.
* **Not W^X.** The NIC can read `.rodata` and can write `.text` if a descriptor says so. (The first
  half of that is a genuine convenience: a hand-built frame template in `@rodata` can be transmitted
  with no copy, because the device does not care that the CPU's mapping is read-only.)
* **Not process isolation.** A descriptor pointing into the ring-3 window would have the NIC write
  into a process's address space, with `m11-proc`'s isolation assertions all still passing.
* **Not `freeFrame`.** **The sharpest hazard here**, and it is the network twin of the one the
  display design found in `procSpaceFree`: `freeFrame` is a bit-clear. Freeing an RX buffer while
  `RCTL.EN` is still set hands that frame to the next `allocFrame` caller **while the NIC is still
  writing packets into it.** There is no diagnostic, at any level. **Rule: clear `RCTL.EN` and
  `TCTL.EN`, and only then free anything** — and nothing in `pmm.dart` will enforce that, so it has
  to be a property of one function in `net.dart` with a comment saying why.
* **No IOMMU.** There is no unit on this machine that could refuse any of the above.

### 3.5 What lives in `@bss`

Small, fixed, and per-driver: the BAR base, the packed BDF, the six MAC bytes, the seven frame
addresses, the RX tail cursor, the TX tail cursor, and counters (TX attempted, TX completed, RX
delivered, timeouts). Call it **`netStore`, one `Bss(bytes: 128, align: 8)`**, addressed through
three accessor functions and nothing else — `pmm.dart`'s "storage seam" comment is the model, and
its warning ("adding a fourth call site is the change that turns a migration into an audit") applies
verbatim.

## 4. The rings themselves

### 4.1 Descriptors are 16 bytes and DCDart cannot spell one

`@packed class … extends Struct` exists and **cannot appear in a signature** (DCDart GAP-0025). So a
descriptor is a base address plus hand-written byte offsets, exactly as `fat.dart` handles directory
entries. Element *i* is at `base + (i << 4)` — a shift, not a walk.

**Legacy TX descriptor** (`e1000_regs.h`'s `struct e1000_tx_desc`):

```
  +0x00  u64  buffer physical address
  +0x08  u16  length                      \
  +0x0A  u8   CSO (checksum offset)        > one dword; the CMD bits below are
  +0x0B  u8   CMD                         /  bits 31:24 of it
  +0x0C  u8   STA (status, low nibble)
  +0x0D  u8   CSS
  +0x0E  u16  special
```

`CMD` bits, given in the header as their position in the dword: `EOP` `0x01000000` → **bit 0 of the
CMD byte**, `IFCS` `0x02000000` → bit 1, `RS` `0x08000000` → bit 3. So the CMD byte for a one-buffer
packet with writeback requested is **`0x0B`** = EOP | IFCS | RS. `STA`'s `DD` is `0x01`.

`IFCS` matters: it asks the NIC to append the Ethernet FCS. Without it, the driver would have to
compute a CRC32 in DCDart, and slirp would drop every frame whose FCS was wrong.

**RX descriptor**:

```
  +0x00  u64  buffer physical address
  +0x08  u16  length (of the received frame)
  +0x0A  u16  packet checksum
  +0x0C  u8   status     DD = 0x01, EOP = 0x02
  +0x0D  u8   errors
  +0x0E  u16  special
```

### 4.2 Head, tail, and the descriptor that is always wasted

Both rings: **the device owns `[HEAD, TAIL)` and software owns the rest.**

* **TX.** Software writes a descriptor at `TDT`, then writes `TDT = (TDT + 1) % N`. That store is
  what starts the transmission. `TDH` catches up; when `TDH == TDT` the ring is idle. Completion is
  the `DD` bit appearing in the descriptor's `STA` byte — **but only if `RS` was set in `CMD`**.
* **RX.** `RDH` is where the NIC will put the next packet. `RDT` is the last descriptor software has
  given it. **Initialise `RDH = 0`, `RDT = N-1`** — not `N` — because `RDH == RDT` means the ring is
  empty and the NIC will drop everything. **One descriptor is permanently unusable**, and that is
  the ring discipline, not an off-by-one.
  Software consumes by polling the descriptor at its own cursor for `DD`, reading the frame, then
  advancing `RDT` to hand the descriptor back.

**The ordering rule, and why nothing has to be written to enforce it:** the descriptor's fields must
be visible to the device before the tail write is. Both are `Pointer<T>` accesses, both are emitted
`volatile` (ADR-0041), and **LLVM may not reorder volatile accesses with respect to each other**;
x86-64's store ordering does not reorder stores with stores. So the requirement is met by the
architecture and by the IR, and **not** by anything the language provides — DCDart has no fence at
all (DCDart GAP-0033). §6 says what that costs and where it stops being free.

### 4.3 Bring-up order

Order matters here in a way it does not in most of this kernel:

```
 1. pciWrite32(cmd, MEM|BME)                     § 1.4 — before anything DMAs
 2. IMC = 0xFFFFFFFF                             mask at the device
 3. CTRL |= RST ; bounded wait ; re-read CTRL    § 5.3 for the bound
 4. IMC = 0xFFFFFFFF                             again: reset re-enabled causes
 5. CTRL |= SLU | ASDE ; CTRL &= ~LRST
 6. FCAL = FCAH = FCT = FCTTV = 0
 7. MTA[0..127] = 0
 8. read RAL0/RAH0 ; read EERD words 0..2        § 2.3
 9. rings: zero both, fill RX buffer addresses
10. RDBAL/RDBAH/RDLEN ; RDH = 0 ; RDT = N-1
11. RCTL = EN|BAM|SECRC|UPE|SZ_2048
12. TDBAL/TDBAH/TDLEN ; TDH = TDT = 0 ; TIPG
13. TCTL = EN|PSP|(0x10<<4)|(0x40<<12)
14. poll STATUS.LU, bounded
```

Steps 6 and 7 are the ones that look droppable. They are also the ones whose absence is invisible
under QEMU (which resets them to zero) and occasionally fatal on hardware — the same class of
difference as ADR-0010 §4.1's BSY-before-DRQ.

## 5. Interrupts versus polling

### 5.1 Recommendation: poll, and make the IRQ its own milestone

**Poll for N0–N6. Build the interrupt path as N7, on its own, with its own exit criterion.**

Polling is: after `TDT`, spin on `DD`; for receive, spin on the RX descriptor's `DD`. Both are
`volatile` loads, so the loop cannot be hoisted away — the failure mode that makes naive polling
loops infinite in C does not exist here.

This is not the ATA argument. ADR-0010 chose PIO because DMA needed things that did not exist;
here the interrupt is a *convenience* whose absence costs responsiveness, not capability. It is
deferred because of what §5.2 costs, and because a command typed at a shell that spins for a
bounded number of iterations is exactly the shape M6 shipped and M14 built a filesystem on.

### 5.2 What the interrupt would actually cost — and it is not one line

**IRQ 11, pin A, verified.** Four separate pieces of work, none of them in `net.dart`:

1. **IRQ 11 is on the *slave* PIC, and the mask is a whole-byte write at six sites.** `picRemap`
   masks the slave completely (`0xFF`) and masks everything but IRQ0 on the master (`0xFE`).
   Reaching IRQ 11 needs the slave's bit 3 cleared *and* the master's **bit 2** cleared — the
   cascade — which has never been unmasked in this kernel's life. **The awkward part is not the
   unmask, it is that every mask write is a literal byte:** `picUnmaskKeyboardOnly` writes `0xFD`
   (`keyboard.dart:173`), `picUnmaskTimerAndKeyboard` writes `0xFC` (`:190`), `picMaskAll` writes
   `0xFF`, and they are called from `kmain.dart:272`, `shell.dart:1085` and `:1090`,
   `proc.dart:2006` and `:2434`, and `vga.dart:426`. **Each of those calls re-masks the cascade**,
   so a NIC interrupt would work until the next `ticks` command or the next process session and
   then silently stop. `m18-preempt` asserts the number of mask and unmask sites *exactly*
   (`MASK_SITES -eq 5`), so this is a change that moves somebody else's structural check as well as
   their golden.
2. **The EOI must go to both PICs**, slave first, then master. `picEoiMaster` is the only EOI that
   exists. An EOI to the master alone leaves the slave's in-service bit set and IRQ 11 never fires
   again; nothing says so.
3. **PCI INTx is level-triggered and shared.** The handler must clear the device's cause (**read
   `ICR`**) *before* the EOI, or the line is still asserted and the interrupt re-fires immediately —
   a livelock, at full speed, with the machine appearing to hang. And because the line is shared, a
   handler that sees `ICR == 0` must conclude "not mine" and EOI without acting, which is a shape
   `isrDispatch`'s if-chain has never had to express.
4. **`m18-preempt` and `m3-shell` have byte-exact goldens over tick behaviour.** GAP-0058 is the
   entry that explains why: the PIT is *masked at rest* precisely so that
   `TICKS 0000000000000064 +0010 LIVE` (`m3-shell/expected.txt:79`) is a fixed string rather than a
   duration. Its own "Cost 1" names the moment this stops working —
   *"the moment something needs a real timebase … the PIT has to stay unmasked, at which point
   `ticks` output becomes non-deterministic and this milestone's golden needs a different shape."*
   Permanently unmasking a second line is the same category of change to the same byte.

The `interrupts.dart` work also **collides with D2** of the display design, which wants the same
file for an input queue. Sequence them; do not let two agents into `isrDispatch` at once.

### 5.3 Every wait is bounded, and the bound is in the compiled code

Five waits: reset completion, link up, EEPROM done, TX `DD`, RX `DD`. Every one is
iteration-counted, on `ataWait`'s model, and returns a value above the register's natural range on
expiry so that "timed out" cannot be confused with "read zero". `m6-disk` disassembles `ataWait` and
requires the bound to survive into the instruction stream; this harness should do the same for
`netWait`, because *"it is bounded in the source"* is not the claim.

**It is an iteration count, not a duration** — GAP-0073, unchanged and now worse: a NIC's link-up
time is genuinely seconds on real copper (§9), so the one number here that a QEMU-tuned bound will
get wrong is exactly the one that decides whether the driver works at all on hardware.

## 6. What DCDart can and cannot express here

**The one place the language is better than C for this job.** Every `Pointer<T>` access is emitted
`volatile` (ADR-0041) — automatically, with no annotation, at every site. For a driver this is not a
tax, it is the correctness property you would otherwise have to remember at every register touch.
ADR-0041's own evidence is worth repeating because it is this exact failure:

> At `-O2` a non-volatile MMIO read-back is deleted outright … **and
> `tests/conformance/m1-pointer/run.sh` still passed**, because the returned value is correct and
> only the access disappeared.

The display design calls volatile-everything a performance ceiling (no vectorised blit). Here it is
load-bearing in the other direction, and the same sentence is the reason.

**What is genuinely missing:**

| wanted | status | consequence here |
|---|---|---|
| a memory **fence** | none — DCDart GAP-0033 | §4.2: covered by x86 TSO + volatile-vs-volatile ordering. **The coverage is architectural, not linguistic.** On any weakly-ordered target this driver is wrong and there is no way to spell the fix. |
| a **struct in a signature** | `@packed` cannot appear in one — DCDart GAP-0025 | descriptors are base + hand-written offsets (§4.1), same as `fat.dart`'s directory entries |
| **arrays** | none | `base + (i << 4)`; the 128-dword `MTA` clear is a `while` loop |
| **multiple return values** | one value, no out-params | `netFindDevice` packs a BDF into a `u64`; every failure is a sentinel, `fat.dart`'s discipline |
| **`switch` / function pointers** | none — DCDart GAP-0023, GAP-0002 | if-chains. With five registers of interest this is not a cost. **oscortex** GAP-0088's warning — LLVM turns a dense `if`-chain into a jump table in a section this repo does not control — applies if the chain grows. |
| **`&&` / `\|\|`** | none — DCDart GAP-0023 | every guard is a chain of single-test `if`s, as everywhere else in this kernel |
| a **byte-swap** intrinsic | none | Ethernet and IP are big-endian; `htons` is `((x & 0xFF) << 8) \| ((x >> 8) & 0xFF)`, expressible and ugly |
| **`String`** | none — DCDart GAP-0035 | every message is a hand-counted `@rodata` byte table, and every count is a fresh instance of GAP-0060 |

**What is no longer missing and whose absence is still commented in this tree:** nested `while`
(ADR-0044), `break`/`continue` (ADR-0047), and 16/32-bit port I/O (ADR-0045 — `Port.outl(u16, u32)`
exists, so `pciWrite32` needs no assembly and `core/boot/portio.S` should not grow). Several
comments in `fat.dart` and `fb.dart` still explain contortions the language no longer requires.
**New code need not contort.**

## 7. The verification apparatus

### 7.1 `filter-dump` gives the host a byte-exact record of the wire

```
-object filter-dump,id=fd0,netdev=n0,file=<path>[,maxlen=N]
```

It attaches to the **netdev**, so it records **both directions**. The output is a classic libpcap
file — verified: magic `d4c3b2a1` (little-endian, µs), version 2.4, snaplen 65535, **linktype 1
(EN10MB)** — and each record is a 16-byte header (`ts_sec, ts_usec, incl_len, orig_len`) followed by
raw bytes. A parser is forty lines of `struct.unpack` with no dependencies, which matters: this
repo's harnesses use `python3` and nothing else (`m5-pci/run.sh:116`).

This slots into the existing harness template with no new machinery: the qemu line already has a
`"$@"` passthrough slot (`m5-pci/run.sh:707`), `qmp-drive.py` already drives keystrokes and captures
serial, and the pcap is just another file compared after the boot — the same shape `m6-disk` uses
for its disk image and `m16-filewrite` for its post-boot FAT walk.

### 7.2 THE VACUITY TRAP, and the one flag that closes it

**A boot that never reaches the kernel already fills the capture.** With a default
`-device e1000,netdev=n0`, QEMU attaches BAR6 — a 256 KiB expansion ROM — and SeaBIOS runs it. I
measured a boot with **no guest OS at all**:

```
#1 dst=ff:ff:ff:ff:ff:ff src=52:54:00:12:34:56 eth=0800   DHCP DISCOVER   439 bytes
#2 dst=ff:ff:ff:ff:ff:ff src=52:55:0a:00:02:02 eth=0800   DHCP OFFER      590 bytes
#3..#6                                                     two more rounds
#7 dst=ff:ff:ff:ff:ff:ff src=52:54:00:12:34:56 eth=0806   ARP             42 bytes
```

Seven packets, **including a full DHCP exchange with the correct guest MAC**, produced by firmware.
Any assertion of the form "the pcap is non-empty", "there is a DHCP exchange", or "the guest MAC
appears on the wire" **passes without a driver.** N6 is the milestone this would have silently
awarded.

**The fix is `romfile=` with an empty value:**

```
-net none \
-netdev user,id=n0 \
-device e1000,netdev=n0,mac=52:54:00:12:34:56,romfile= \
-object filter-dump,id=fd0,netdev=n0,file="$WORKDIR/net.pcap"
```

Verified: BAR6 disappears, and the capture is **24 bytes — header only, zero packets**. Verified
again with `core/build/kernel.elf` itself: today's kernel, booted for 12 seconds with this exact
flag set, transmits **nothing**. The negative control of N2 is already true and can be regression-
tested from the day the harness is written.

Two more notes on those flags. `-net none` suppresses the legacy default NIC (belt and braces —
supplying `-netdev` already does), and the explicit `mac=` is what makes the expectation **derived
from the command line** rather than from QEMU's `52:54:00:12:34:56` default, which is a default and
therefore not ours (`m5-pci/run.sh:686` makes exactly this argument about `-vga std`). With these
flags the NIC is still at **`00:03.0`** and BAR0 still at **`0xFEBC0000`** — measured.

### 7.3 Why slirp's *reply* is the strongest evidence available

`-netdev user` is a userspace TCP/IP stack. It will answer:

* an **ARP request** for `10.0.2.2`, with an ARP reply;
* an **ICMP echo request** to `10.0.2.2`, with an echo reply;
* a **DHCP DISCOVER**, with an OFFER of `10.0.2.15`.

**This is worth more than the pcap.** The pcap proves bytes left the machine. A *reply* proves an
independent implementation, written by other people for other reasons, **parsed those bytes and
found them well-formed** — including, for ICMP and UDP, that the checksums are arithmetically
correct, because slirp drops a bad-checksum datagram silently and answers nothing. N5's exit
criterion is therefore a checksum test that nobody had to write a checksum test for.

It is `m6-disk`'s "negative control B" argument in a new domain: the thing that makes a hexdump
evidence of a disk rather than something the kernel can produce on its own.

**Do not hard-code `52:55:0a:00:02:02`.** I observed it and it is a slirp implementation detail.
Assert the ARP reply's **sender-protocol-address** (`10.0.2.2`, which comes from the `net=`/`host=`
arguments the harness itself passes) and the **target-hardware-address** (our `mac=`, likewise ours).
Both are derived from the command line; the gateway's MAC is not.

### 7.4 Two cross-checks the existing harness machinery already supports

* **`info pci` through QMP** (`--monitor-command`, as `m5-pci` already does) gives QEMU's own view of
  BAR0. Comparing it with the number the kernel printed is two independent observers of one fact —
  the same structure as `m6-disk` cross-checking capacity against the image file's real byte count.
* **`xp` at an address the kernel printed** (`--addr-from-serial 'NET RXBUF ([0-9A-F]{8})'` plus
  `--monitor-command 'xp/16wx {addr}'`, exactly `m5-pci`'s framebuffer sweep) lets the host read the
  RX buffer **out of guest RAM** and compare it byte-for-byte with the packet in the pcap. That is
  the single sharpest assertion available in this whole document: the same frame, seen by the host's
  capture and by the guest's memory, required to be equal.

## 8. The milestone ladder

Format follows the display design: each milestone states its blocker, its binary exit criterion, and
a negative control. **Every expectation is derived** — from the `mac=` and `net=` arguments the
harness itself passes, from a frame the harness builds byte by byte, or from a second observer —
never from a captured run that was eyeballed once.

All boots use the flag set in §7.2.

---

### N0 — The device is named, and its BAR is a number the kernel read

**Blocked on: nothing.** `pci.dart` and `fb.dart` between them already contain every technique.

`net info`: walk bus 0 for class `02`/`00`, print BDF, vendor:device, BAR0, the command register
**before and after** the BME write, the interrupt line from config `0x3C`, and the MAC from both
`RAL0`/`RAH0` and `EERD`. Adds `pciWrite32` (§1.4).

*Binary:* the BAR0 the kernel prints equals the `address` QMP `query-pci` reports for `00:03.0`
(independent observer); the printed MAC equals the `mac=` on the QEMU command line (derived); the
EERD-derived MAC equals the RAL/RAH-derived MAC (decoding check, §2.3); the command register's bit 2
is **set** in the "after" value; the interrupt line reads `11`.
*Negative control:* the same kernel booted with `-net none` and no `-device` must print `NET NONE`
and no BAR line at all — and the harness must grep for the BAR-shaped line and require it absent.
*Anti-vacuity:* fail if the "before" and "after" command-register values are absent from the capture,
so a build that prints one number twice cannot pass.

---

### N1 — It is reset, and the link is up

**Blocked on: N0.**

Steps 1–8 and 14 of §4.3. Introduces `netWait`, the bounded poll (§5.3).

*Binary:* `STATUS` is printed before and after; `LU` is 0 before `SLU` is written and 1 after; the
harness asserts both, so a kernel that prints a constant fails. `CTRL` re-read after `RST` has
`RST` clear.
*Negative control:* **QMP `set_link n0 off` before the command runs.** The kernel must report
`NET LINKDOWN` after its bounded wait expires, and must **not** proceed to enable the rings. This is
the assertion that proves the link check is a check.
*Structural:* `netWait`'s iteration bound must survive into the disassembly, `m6-disk`-style.

---

### N2 — One frame leaves the machine

**Blocked on: N1.** The first milestone where this kernel causes an effect outside itself.

TX ring set up (§4.3 steps 12–13); one hand-built ARP request for `10.0.2.2` in a `@bss` frame
template, copied from `@rodata` with the source MAC patched from `RAL0`/`RAH0`; descriptor written;
`TDT` advanced; `DD` awaited.

*Binary:* the pcap contains **exactly one** packet, and its bytes equal the 60-byte frame the
harness built independently from the `mac=` argument and the chosen target IP — **byte for byte,
including the pad to 60 and excluding the FCS the NIC appends**. `TPT` (§2.2, the device's own
counter) reads exactly 1.
*Negative control A — and it is the one that matters:* **a build with the BME write removed.** The
same keystrokes, the same everything, and the pcap must contain **zero** packets. That is the proof
that the packet travelled by DMA rather than by anything the kernel could have faked, and it is the
only assertion here that distinguishes "the NIC transmitted" from "the driver believes it did".
*Negative control B:* a boot that never types the command → zero packets (already true today, §7.2).

---

### N3 — The device acknowledges the transmit

**Blocked on: N2.**

Assert the writeback rather than the wire: print the TX descriptor's `STA` byte after the wait.

*Binary:* `STA` reads `0x01` (`DD`), and `TDH == TDT`.
*Negative control:* **a build with `RS` cleared in the CMD byte.** `DD` must never appear, the
bounded wait must expire, the kernel must print its timeout diagnostic — **and the pcap must still
contain the packet.** That double assertion is what proves `RS` controls the *writeback* and not the
*transmission*, which is the single most common misunderstanding of this descriptor format.

---

### N4 — A frame arrives, and two independent observers agree on its bytes

**Blocked on: N2.** The milestone the whole design exists for.

RX ring set up; `RDT = N-1`; send the N2 ARP request; poll the RX descriptor for `DD`; print the
received length and a hexdump of the frame, `ata.dart`-style, as it is read.

*Binary:* three things at once.
1. the pcap contains **exactly two** packets, and #2 is an ARP **reply** whose sender-protocol-address
   is `10.0.2.2` (derived from the harness's `net=`) and whose target-hardware-address is our `mac=`;
2. the length the kernel printed equals packet #2's length in the pcap, **exactly** — which is where
   `RCTL.SECRC` is really tested, since without it the guest's length is four bytes longer;
3. the guest's hexdump equals packet #2's bytes. **Host capture and guest memory, required equal.**

*Negative control:* **a build that never writes `RDT`**, leaving `RDH == RDT`. The reply must still
appear in the pcap and the kernel must print `NET RX NONE`. That separates "the wire" from "the
ring", and it is the control that catches a driver which is reporting a packet it did not receive.
*Anti-vacuity:* fail if the expected hexdump is zero bytes long.

---

### N5 — The checksums are right, and something else says so

**Blocked on: N4.**

An ICMP echo request to `10.0.2.2`, built in DCDart: IP header with its own checksum, ICMP header
with its own, a fixed payload, a chosen identifier and sequence number.

*Binary:* the pcap contains the request and a **reply**; the kernel prints the reply's identifier and
sequence and they equal the ones it sent (derived, since the harness chooses them). **Slirp answering
at all is the checksum assertion** — a bad IP or ICMP checksum is dropped silently, so there is no
reply to find.
*Negative control:* a build with one byte of the IP checksum inverted. The request must still appear
in the pcap (we transmitted) and there must be **no reply** (nobody believed us). Two facts, one
boot, and neither is available from inside the guest.

---

### N6 — It gets an address from a server it did not write

**Blocked on: N5** (UDP wants the same checksum machinery, plus a pseudo-header).

DHCP DISCOVER → OFFER. Requires parsing a variable-length options field, which is the first thing
this kernel has ever parsed that is not fixed-layout.

*Binary:* the kernel prints the offered address and it equals `net|15` — **derived** by the harness
from its own `-netdev user,net=…` argument. The transaction ID in the OFFER equals the one the
kernel generated.
*Negative control:* **a second boot with `net=192.168.76.0/24`.** The expectation moves to
`192.168.76.15`, so a kernel printing a constant passes one boot and cannot pass both. I measured
this rule rather than assuming it (§0.1): slirp offers `net|15` and answers from `net|2`.
**This is the milestone §7.2's trap was aimed at.** Without `romfile=`, the firmware's own DHCP
exchange is in the capture and this criterion passes on a kernel that does nothing.

---

### N7 — The interrupt path

**Blocked on: N4, and on §5.2's four pieces of work in `interrupts.dart` — which collide with the
display design's D2.** Sequence, do not parallelise.

Slave-PIC unmask, cascade unmask, two-PIC EOI, `ICR`-read-before-EOI, a shared-line "not mine" arm.

*Binary:* two boots. **(a)** with `IMS = RXT0` set, a received packet increments an
interrupt counter in `@bss`, printed by `net info`, from 0 to exactly 1. **(b)** the same counter
advances when the driver writes **`ICS`** with no packet at all — which tests the delivery path
independently of the RX path, and is the only way to test it without a wire.
*Negative control:* IRQ 11 left masked at the PIC. The packet must still appear in the pcap and in
the RX ring (polled), and the counter must stay **0**. That separates "the interrupt fired" from
"the packet arrived", which is otherwise indistinguishable from the serial capture.
*Regression:* every harness that asserts a byte-exact serial golden must be re-run, and
`m18-preempt`'s exact-count checks on the mask/unmask call sites (§5.2 item 1) will fail by
construction. **Budget that; do not discover it.**

---

### Named successors, not milestones

* **A packet a *program* can see.** N0–N7 end at a shell command that prints. There is no syscall,
  no socket, no queue, and — GAP-0141 — **nothing to block on**, so `recv` cannot exist in the shape
  anyone expects. This is exactly ADR-0010 §5's *"can SHOW you a sector and cannot GIVE you one"*,
  one layer up, and unlike M6 the reason is no longer the allocator.
* **TCP.** Not close. It needs timers, retransmission, and a place for connection state to live
  across commands — which is the display design's D3 (a resident process) wearing different clothes.
* **The recursive bus search** (§1.1), **`RCTL.BSEX` buffers** (§3.3), **MSI** (GAP-0067 item 4, and
  the reason `0x34` is never followed), and **a second NIC** (nothing in this design is per-device;
  `netStore` is a singleton and says so).

## 9. Where QEMU is more forgiving than silicon

Four places, each of which is a way to pass every criterion in §8 and fail on a real 82540EM. This
is ADR-0010 §4.1's section, and it exists because that section was right.

1. **Link-up is instantaneous.** QEMU sets `STATUS.LU` as soon as the netdev is attached. Real copper
   auto-negotiation takes **up to two seconds**. An iteration bound tuned until N1 passes will be one
   or two orders of magnitude too small, and the driver will report `LINKDOWN` on hardware. GAP-0073
   again, and this is its worst instance: there is no calibrated delay in this kernel to use instead.
2. **Transmit completes synchronously.** QEMU's `start_xmit` runs inside the vCPU's `TDT` write, so
   `DD` is already set by the time the store returns. **A driver that never polls `DD` passes N2 and
   N3.** N3's `RS`-cleared negative control is the only thing in this ladder that notices, which is
   why it is written the way it is.
3. **Registers reset to convenient values.** QEMU zeroes `MTA` and the flow-control registers on
   reset. Hardware does not promise that. Steps 6 and 7 of §4.3 are untestable here and must be
   written anyway.
4. **The PHY is a stub.** `MDIC` returns canned values. Anything that depends on reading real PHY
   state — link partner ability, speed resolution — cannot be developed against this target at all,
   which is a reason to depend on `STATUS` and nothing else.

**And one that cuts the other way:** the WB mapping of the PCI hole (§1.2) is a *hardware* bug that
QEMU cannot exhibit, because a QEMU MMIO access is a memory-region dispatch and no cache is involved.

## 10. What I did not decide, and would rather be told

**Q0 — Is a NIC the right next milestone at all?** The display design nominates D3 (a resident
process) as the thing everything waits on, and it is not wrong. N0–N5 are genuinely independent of
it and genuinely useful — but N-anything-beyond-N6 wants a resident process for the same reason a
compositor does. **If D3 is being built, this ladder should stop at N5 and wait.**

**Q1 — Poll or interrupt first?** §5.1 recommends polling and §5.2 prices the alternative at four
changes in a file two other units want. If the answer is "interrupts first because the PIC work is
owed anyway", that is a legitimate call and it changes the order of the ladder, not its content.

**Q2 — `@bss` or `allocFrame` for the rings?** §3.3 recommends the allocator and gives the reasoning
(28 KiB, returnable, not paid for by machines with no NIC). The counter-argument is real: `@bss`
costs zero allocator frames, cannot fail, and makes the ring addresses **link-time constants a
harness can read out of the symbol table** — which is a materially stronger structural check than
anything available for a runtime address. **If harness strength is the priority, `@bss` wins**, and
I would rather be told than pick.

**Q3 — Should `pciWrite32` live in `pci.dart`?** It is a PCI facility, not a network one, and putting
it there means the next driver does not re-invent it. It also means `m5-pci`'s structural checks —
including its "no `port_outl` to `0xCFC` anywhere" property, if it has one — change in a unit whose
subject is a NIC. ADR-0010 §6 declined exactly this kind of two-changes-one-commit and I would
follow it: put it in `pci.dart`, land it **as its own unit**, then build N0 on it.

**Q4 — How much honesty is wanted in the ADR about `romfile=`?** §7.2 is a finding about the
*harness*, not the kernel, and it invalidates the obvious version of two exit criteria. It belongs in
`known-gaps.md` where the next person to write a device harness will find it, and I have not written
it there.

## 11. Notes for the coordinator to fold in elsewhere

**I have not touched `known-gaps.md` or `ROADMAP.md`, per instruction.** These are the entries that
belong in them, with reasoning, for whoever folds them in.

* **The PCI hole is mapped write-back with no `PCD` and no MTRR programming** (§1.2). True today,
  invisible under QEMU, wrong on hardware, and it affects `fb.dart` **right now** — not just this
  design. It is the one item here that is a defect in shipped code rather than a property of
  unwritten code.
* **`freeFrame` has a DMA twin of the display design's use-after-free** (§3.4). If a frame the NIC is
  writing into is freed, `pmm.dart` hands it to the next caller with no diagnostic at any level. The
  display design already asked for a `freeFrame` lifetime entry; this is the same entry with a second
  reason, and the second reason is worse because a device keeps writing after the process is gone.
* **QEMU's e1000 I/O BAR is a stub** (§1.3). Worth recording as a general caution — an emulated
  compatibility path may be decoded and not implemented — because the next agent to look for a PIO
  shortcut will find the same BAR and make the same assumption I did.
* **The option-ROM vacuity trap** (§7.2), with the flag that closes it. This is reusable knowledge
  for any future device harness, not a network fact.
* **GAP-0067 items 2 and 8 both get closed by N0** — configuration space becomes writable, and the
  e1000 stops being "found and named and then left alone". Item 3 (BARs not read) closes too.
  Whoever lands N0 should update that entry rather than leave three items reading as open.
* **A `--pcap` sibling for the harness template.** `qmp-drive.py` needs no change at all — the pcap
  is written by QEMU and parsed after the boot — but the `-object filter-dump` flags and a small
  `pcap.py` parser will be copied into every network harness unless somebody puts them somewhere
  shared. There is no shared shell library in this repo (every `run.sh` re-declares `fail()`), so
  "somewhere shared" means a Python file referenced by absolute path, exactly as
  `m2-console/qmp-drive.py` already is.
* **`DCDart/core/runtime/dc-core-bare/prelude.dart:551` is stale.** It says `Pointer<T>` has "no
  `@volatile` semantics yet"; ADR-0041 implemented them and `dcc-lower` sets `isVolatile` at both
  sites. That comment is exactly the kind a driver author reads and then works around. **The fix
  belongs in the DCDart repo**, not this one.
