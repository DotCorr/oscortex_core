# ADR-0025 — SMEP is enabled when the CPU has it. **SMAP is not, and the four lines of kernel that stop it are named.**

**Status:** accepted, implemented, verified (`core/tests/conformance/m11-proc/run.sh`, three CPU models)
— **the bit is proved SET; it is NOT proved to BLOCK anything. See §5, which is the honest part of
this document.**
**Date:** 2026-08-23
**Part of:** a fix batch, not a milestone. No `ROADMAP.md` entry.
**Records:** GAP-0153. **Narrows:** GAP-0085 item 6, ADR-0013 §10 ("No SMEP, no SMAP, no PCID").

---

## 1. What was built

Seventeen lines in `core/boot/boot.S`, in 32-bit protected mode, before long mode:

* a CPUID **leaf 7, subleaf 0** probe — `EBX[7]` is SMEP — whose answer is left in `ESI`;
* `orl $0x100000, %eax` folded into the **existing single CR4 write**, under `testl %esi, %esi`.

Zero DCDart changes. Zero new externs (still 44). Zero new `.bss`. Zero new shell commands.

**It does NOT move zero goldens, and the claim that it does was worth checking.** The audit that
proposed this said SMEP was "measured to move zero goldens". That is true of the *`CR4` value* — plain
`qemu64` has neither feature, so `CR4` stays `0x620` and nothing that prints `CR4` changes. It is
false of the goldens. Measured, by linking four kernels and reading the section headers:

| build | `.text` end | `.rodata` end | `.bss` |
|---|---|---|---|
| HEAD | `0x131820` | `0x135CAE` | 71728 |
| + SMEP only | `0x131850` (**+48**) | unchanged | unchanged |
| + the read-only fix only | `0x131910` (+240) | `0x135D0A` (+92) | unchanged |
| both (shipped) | `0x131940` (+288) | `0x135D0A` (+92) | unchanged |

**Forty-eight bytes of `.text` is not zero**, and three goldens — `m8-paging`, `m9-ring3`,
`m10-elf` — print a `VM SECT` line carrying the kernel's own section extents. All three move. Any
change that adds an instruction to this kernel moves them; that is a property of what those goldens
chose to record, not of this change. The correct statement is **"`CR4` is unchanged on every existing
boot"**, which is asserted in `m11-proc`, and that is what the no-golden claim should have said.

## 2. Why the answer is a register and not a flag

`nx_flag` and `sse_flag` are stored in `boot.S`'s `.bss` because DCDart **reads** them: `vm.dart` must
know whether bit 63 of a page-table entry is NX or a reserved-bit violation, and `proc.dart` must know
whether `fxsave` is a `#UD`. Nothing in this kernel needs to know whether SMEP is on. SMEP changes no
code path — it makes one impossible.

Storing it would have meant an eight-byte `.bss` symbol plus an `smep_enabled()` accessor, and an
accessor is a **new extern**, whose count eight harnesses assert. That is a real cost for a fact with
no reader — and a declared constant with no reader is precisely the defect ADR-0024 had just finished
fixing. `cr4_read()` already exists and reports the bit *as the CPU holds it*, which is a better
answer than a copy of what the boot stub intended.

## 3. Why SMAP is not set, which is the substantive decision here

SMAP makes a supervisor **data** access to a user page a `#PF`. This kernel performs exactly four,
and I read all 160 `Pointer<…>.fromAddress` sites in `core/kernel/` to be sure the count is four:

| # | Site | Direction | Validator |
|---|---|---|---|
| 1 | `user.dart:1393` — `uartWrite(ptr, len)` in `userSysWrite` | read | `userOwns` |
| 2 | `file.dart:1398` — `open`'s name copy | read | `elfOwns` |
| 3 | `file.dart:975` — `fileCopyIn` (`fdwrite`'s source) | read | `fileOwnsRead` |
| 4 | `file.dart:811` — `fileCopyOut` (`read`'s destination) | write | `fileOwnsWrite` |

**With `CR4.SMAP` set, every one of those faults.** `open()` from ring 3 — the first syscall
m15-fileio and m16-filewrite make — would `#PF` inside the kernel. Enabling SMAP today means shipping
a kernel that works only on CPUs that do not have the feature, which is worse than not shipping it.

**The ELF loader and `args.dart` are not among the four**, and the reason is the shape the other four
would have to take. `elfCopyPageBytes` writes at `frame + lo` — the frame's **identity address**, before
`vmProgMap` has run at all — and `argsBuild` goes through `argsPhys(frame, va) = frame + (va -
vmProgStackPage)`, whose own header says *"the two addresses of one byte differ by a constant"*. Both
touch the physical alias, which is a supervisor mapping, so both are already SMAP-clean.

Sites 2, 3 and 4 could be converted the same way: their pages are in `[vmProgBase, vmProgEnd)` =
`[0x10000000, 0x10200000)`, every frame behind them is below 128 MiB, and `vmProgLeaf` already does
the VA→leaf walk that would find the physical address. It is not a one-liner — a copy that crosses a
page boundary has to walk per page — but it is ordinary work.

**Site 1 cannot be converted at all, and that is the finding this ADR exists to record.** The M9
payload path does not map ring 3 into a separate window; `vmMapUser` flips the U/S bit **in place,
inside the 4 KiB identity map**, so for that page *the user virtual address is the physical address*
and there is no supervisor alias to reach it by. `userOwns` bounds ring 3 to `< vmFineBytes` (4 MiB),
which is the identity region itself. Converting site 1 means either `stac`/`clac` (two new externs,
and eight harnesses' extern counts move), a second supervisor mapping of the same frame, or dropping
the `user` command from any `+smap` boot.

So SMAP is one design decision behind SMEP, not one instruction behind it. `boot.S` does not even
probe for it: an answer nothing may act on is storage with no reader, and §2 explains why this file
does not do that any more.

## 4. What is proved

`m11-proc` already owned the `CR4` line — it prints it (`procSseLine`), asserts its OSFXSR bits, and
already boots a `-cpu qemu64,-sse,-fxsr` machine to check `CR4` comes back as **exactly** `0x20`. Two
more CPU models were added there rather than in `m8-paging`, which cannot see `CR4` at all:

| boot | CR4 | what it establishes |
|---|---|---|
| `-cpu qemu64` (every existing boot) | `0000000000000620` | **unchanged.** `qemu64` reports `smep=false`, the probe finds nothing, and not one golden in the repo moves |
| `-cpu qemu64,-sse,-fxsr` | `0000000000000020` | the pre-existing negative control still holds |
| `-cpu qemu64,+smep` | `0000000000100620` | the probe found the feature and the bit is really in `CR4` |
| `-cpu qemu64,+smep,+smap` | `0000000000100620` | **SMAP is deliberately not set**, asserted mechanically rather than left as prose in this file |

The last row is the one that is easy to leave out. Without it, "we chose not to enable SMAP" is a
sentence in a document that nothing checks, and the difference between that and a probe that silently
sets both bits is one `orl` nobody would notice.

## 5. What is NOT proved, stated plainly

**No boot in this repo shows SMEP refusing an instruction fetch.** Every check above is a read-back of
`CR4` plus "the machine still boots and still runs a ring-3 program with the bit on". That is evidence
the bit is set and harmless. It is **not** evidence that the protection works, and this ADR does not
imply otherwise. `security.md` §5.5 calls this the vacuity trap and it is right to.

The demonstration is reachable and the recipe is known — the pieces already exist, which is why it is
worth writing down rather than waving at:

* `vm_exec_probe(addr)` (`isr.S:816`) does `call *%rdi` and is **already an extern**, so the positive
  test costs no new one. `vmtest nx` is the same shape against a non-executable page.
* `vmMapUser(va, exec=1)` (`vm.dart:1763`) makes a 4 KiB identity page user-accessible and executable.
* So `vmtest smep` = map a page holding a `ret` as user+exec, `vm_exec_probe` it, and require `#PF ERR
  0x11` (present, read, supervisor, **instruction fetch**) on a `+smep` boot and a clean return on a
  plain `qemu64` one. The pair is what makes it non-vacuous.

**What stopped it being done in this batch, and it is not "no time":** the faulting probe never
returns. `fault_resume` abandons the stack and re-enters the shell loop, so the `vmClearUser` that
would put the page back to supervisor is skipped **on exactly the run where the test succeeds** — and
the machine is left with a user-accessible kernel page. A diagnostic command that leaves a hole
behind when it proves the hole is closed is not a good trade, and closing it properly means
fault-path cleanup (a pending-restore note the shell loop honours), a new `vmtest` sub-command, a
longer `vmStrTestUsage` and a regenerated `m8-paging` golden. That is a milestone-shaped change and
this is a fix batch.

**So: SMEP here is correct-and-unproven, and it is shipped as that.** It is not shipped as
demonstrated. GAP-0153 carries the residual.

## 6. The trap this avoided

CR4 bit 20 is **reserved** on a CPU without SMEP, and writing a reserved CR4 bit is a `#GP`. At this
point in `boot.S` there is no IDT, so a `#GP` is a triple fault: a VM that reboots silently with no
output at all. That is exactly what `EFER.NXE` did at M8, and exactly what CR4 bits 9/10 would do
without `sse_flag`. Hence the probe, and hence the maximum-leaf comparison in front of it — `cpuid`
asked for a leaf above the maximum returns the **highest** leaf's data, not zeroes, so "leaf 7 says
EBX[7]" on a Nehalem is a coin flip on some other leaf's register.
